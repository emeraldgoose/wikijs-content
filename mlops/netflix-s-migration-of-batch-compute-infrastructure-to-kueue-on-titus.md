# Netflix's Migration of Batch Compute Infrastructure to Kueue on Titus

> **Level**: Advanced  
> **Source**: [How Netflix Simplified Batch Compute with Kueue](#)  
> **Last Updated**: 2026-08-28

## Introduction

Netflix's migration of batch compute infrastructure to Kueue on Titus is the transition from the proprietary Compute Managed Batch system to a Kubernetes-native job queueing system within the Titus container platform. This initiative matters as it aligns infrastructure with Kubernetes standards, replacing custom scheduling logic to simplify operations at scale. Primary use cases include managing millions of completion-oriented workloads, enforcing tenant-based capacity reservations, and federating workload execution across multiple Kubernetes clusters without requiring direct topology control. Ultimately, the migration standardizes resource management for distributed batch processing tasks while maintaining high availability across cells.

## Core Concepts

### Concept 1: Transition to Kubernetes-Native Batch Orchestration
*   **Motivation:** The migration is driven by Netflix's goal to transition compute infrastructure to be more Kubernetes-native.
*   **Tool Adoption:** The platform incorporates components from the Kubernetes ecosystem, specifically adopting **Kueue** as the job queueing system.
*   **Logic Replacement:** Kueue largely replaces the custom queuing and scheduling logic previously housed in the homegrown managed batch solution, Compute Managed Batch (CMB).
*   **Simplification:** This shift aims to simplify batch compute management by utilizing established cloud-native standards rather than custom-built logic.

### Concept 2: Titus Platform and Cluster Federation
*   **Execution Layer:** **Titus** serves as the underlying container platform where batch workloads are submitted and executed to completion.
*   **Workload Federation:** The infrastructure supports workload federation across multiple cells, which are distinct Kubernetes clusters.
*   **Topological Abstraction:** Federated capacity reservations allow users to interact with a single Titus endpoint without needing to understand the underlying cell or cluster topology.
*   **Capacity Reservations:** The system manages capacity reservations in a federated manner, decoupling workload submission from specific cluster locations.

### Concept 3: Tenant Hierarchy and Workload Prioritization
*   **Grouping Mechanism:** **Tenants** act as the primary grouping mechanism for jobs, representing organizations, platforms, or applications.
*   **Flexible Structure:** Users can organize tenants to suit specific needs, ranging from a single tenant across applications to complex hierarchies matching team ownership.
*   **Ordered Execution:** Workloads queued under specific tenants are processed with ordered execution based on assigned priorities.
*   **Management Scope:** Workload management and queuing logic are governed by the tenant hierarchy associated with each submission.

### Concept 4: Per-Tenant Capacity Configuration
*   **Association:** Every tenant is linked to a specific capacity configuration that dictates their resource usage limits.
*   **Resource Management:** Compute capacity is managed strictly on a per-tenant basis to ensure fair and controlled resource distribution.
*   **Defineable Limits:** The capacity configuration explicitly defines the amount of compute capacity available to a specific tenant.
*   **Isolation:** This structure ensures that capacity provisioning is isolated and reserved according to the defined configuration for each tenant.
