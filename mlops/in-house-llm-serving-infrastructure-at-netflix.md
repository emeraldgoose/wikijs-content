# In-House LLM Serving Infrastructure at Netflix

> **Level**: Advanced  
> **Source**: [In-House LLM Serving at Netflix](#)  
> **Last Updated**: 2026-08-28

## Introduction

Netflix's In-House LLM Serving Infrastructure is a proprietary system designed to deploy and execute large language models within its production environment rather than utilizing external hosted APIs. This architecture integrates with a unified JVM-based serving system, enabling end-to-end control over routing, A/B testing, and feature fetching without separate ML silos. Key deployment strategies include running small CPU models in-process to minimize overhead and delegating larger GPU workloads to remote services. The system supports both gRPC and direct HTTP inference paths, accommodating member-scale machine learning operations for downstream consumers. Operational decisions regarding engine selection, model packaging, and output constraints prioritize production adaptability and cost optimization over external service consumption.

## Core Concepts

### Concept 1: End-to-End In-House Serving Strategy
*   Netflix chose to run the complete LLM stack internally, from model deployment through inference, rather than consuming hosted APIs like most organizations.
*   The infrastructure operates within the existing production environment instead of relying on a separate ML silo.
*   Decisions regarding engine selection, packaging, and API design were validated under production load to reveal trade-offs not anticipated during the design phase.

### Concept 2: Unified JVM-Based Serving System
*   A single JVM-based system fronts member-scale ML to handle the end-to-end flow for downstream consumers.
*   This system manages routing, A/B test logic, candidate generation, feature fetching, inference, post-processing, and logging at every stage.
*   It supports both real-time and cached batch paths.
*   Clients can access inference via two methods: a gRPC path through the serving system or a direct HTTP path used by newer LLM-driven applications.

### Concept 3: Model Scoring Service (MSS) and Triton Integration
*   The Model Scoring Service (MSS) serves as the shared inference backend for larger models that require GPUs.
*   It provides a unified interface supporting XGBoost, TensorFlow, PyTorch, and LLMs.
*   The NVIDIA Triton Inference Server operates underneath MSS to manage model loading, batching, and GPU scheduling.
*   The local serving system handles pre- and post-processing while delegating the actual inference task to the remote MSS.

### Concept 4: Java Control Plane Management
*   A Java control plane sits on top of the Triton server to handle operational governance.
*   Key responsibilities include deployment, versioning, health checking, autoscaling, and multi-region rollout.
*   Model authors are responsible for packaging artifacts and configuring the deployment.
*   The control plane provisions GPU instances and configures the underlying Triton infrastructure based on these configurations.

### Concept 5: Hardware-Aware Inference Routing
*   The location where inference runs is determined by the specific model requirements.
*   Small CPU models execute in-process to avoid the overhead of remote calls.
*   Larger models requiring GPU acceleration are routed to the remote Model Scoring Service.
*   This hybrid approach optimizes performance by balancing latency overhead with hardware capabilities.
