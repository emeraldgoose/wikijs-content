# Netflix's migration of batch compute infrastructure from Compute Managed Batch (CMB) to Kueue on the Titus platform

> **Level**: Advanced  
> **Source**: [How Netflix Simplified Batch Compute with Kueue](#)  
> **Last Updated**: 2026-08-28

## Introduction

Netflix's migration of batch compute infrastructure from Compute Managed Batch (CMB) to Kueue on the Titus platform is the transition of workload management from a custom homegrown solution to a cloud-native Kubernetes job queueing system. This initiative aligns Netflix’s container platform with Kubernetes standards, replacing proprietary logic to simplify operations and enhance scalability. Primary use cases encompass batch jobs requiring ordered execution, priority-based scheduling, and per-tenant capacity reservation across federated Kubernetes clusters. By adopting Kueue, the platform provides a unified endpoint for workload submission while abstracting underlying cell topology. This shift reduces technical debt associated with custom tooling and standardizes batch processing within the Titus ecosystem at a scale of millions of jobs.

## Core Concepts

### Concept 1: Kubernetes-Native Migration Strategy and Kueue Adoption
*   **Objective:** Transition Netflix’s compute infrastructure to be more Kubernetes-native by integrating components from the Kubernetes ecosystem into the Titus container platform.
*   **Implementation:** Incorporating Kueue, a cloud-native job queueing system designed specifically for batch workloads.
*   **Replacement Goal:** Replace custom queuing and scheduling logic found in the homegrown Compute Managed Batch (CMB) solution with standardized Kubernetes tools.
*   **Scale:** The migration supports the management of millions of batch jobs running on the platform.

### Concept 2: Compute Managed Batch (CMB) Legacy Architecture
*   **Functionality:** CMB served as a managed batch solution allowing users and applications to execute workloads that run to completion.
*   **Job Management:** It handled queuing and ordered execution logic based on defined priorities for workloads.
*   **User Interface:** Developers could submit workloads, get status updates, and manage capacity through a single Titus endpoint.
*   **Limitation:** As a homegrown solution, it contained custom queuing logic that the migration aims to abstract or replace with Kueue.

### Concept 3: Titus Platform Federation and Abstraction
*   **Base Layer:** Titus is the underlying container platform on which workloads managed by CMB (and potentially Kueue) are executed.
*   **Multi-Cell Federation:** Titus supports workload federation across multiple cells, which are individual Kubernetes clusters.
*   **Topology Abstraction:** CMB and the migrating batch infrastructure can interact with a single endpoint without needing to handle the complexity of the underlying cell or cluster topology.
*   **Resource Reservations:** The platform manages federated capacity reservations, allowing centralized capacity updates across the distributed cluster infrastructure.

### Concept 4: Tenant Hierarchy and Capacity Configuration
*   **Grouping Mechanism:** Tenants provide a structure to group jobs submitted on behalf of specific organizations, platforms, or applications.
*   **Flexible Hierarchy:** Users can organize tenants to match their internal team structures or application ownership models, using single tenants or complex hierarchical trees.
*   **Capacity Association:** Each tenant is linked to a specific capacity configuration.
*   **Resource Definition:** Capacity configurations define the amount of compute resources available to a specific tenant, with capacity managed on a per-tenant basis to ensure isolation and allocation.
